# Re-prefill on failover: in-flight requests keep their context

Source: `integrations/vllm/patches/patch_external_pp_reprefill.py` (patch 14, runner + `v1/core/sched/scheduler.py`), pure logic in `external_pp_reprefill.py` (inlined into the runner), communicator change in `integrations/vllm/connexte_communicator.py` (`_get_peer_endpoint`), tests in `tests/test_reprefill.py`, cluster harness `benchmarks/k8s/failover_correctness.py`. Fork: external-PP vLLM fork 380186d57. Flag `CONNEX_PP_REPREFILL` (default 1), `CONNEX_PP_REPREFILL_MAX` (default 8).

## Root cause
KV is per request on every stage. When a downstream replica dies or leaves, the upstream neighbour fails over to a surviving replica of that stage (sticky peer) and the step is re-sent. The surviving replica never saw those requests: its allocator creates a fresh entry, the block table points at the null block, and it runs the decode step against an empty context. Nothing tells stage 0, so the request keeps decoding with whatever KV the new chain accumulates from then on. The outputs look like text but are not the model's output. The same silent failure happens when a replica restarts under the same identity, when the downstream allocator reclaims a request (TTL or LRU on exhaustion), and when a stage-0 prefix-cache hit reaches a downstream replica that does not hold that prefix.

Evidence (K=4, 16 concurrent greedy requests of 300 tokens on chain 1, stage 2 replica 1 SIGKILLed 3 s in, `CONNEX_PP_REPREFILL=0`): all 16 requests diverge from the churn-free reference at token 79-86, the failover point, and teacher-forced scoring finds 596 of 4800 generated tokens that are not the argmax of their own prefix (worst gap 21.5 nats). A churn-free run has 0 such tokens (worst gap 0.06-0.13 nats).

## Design
The downstream stages are the only place that knows what KV they hold, so they detect, and stage 0 is the only place that can recompute, so it repairs.

* Contract: stage 0 sends `cx_ctx` (its `num_computed_tokens` per request) on every step. A stage holds `kv_len` tokens for a request if it wrote them itself and the request is still live in its allocator; for a prefill-type step its own computed prefix-cache blocks also count. A request with `cx_ctx > held` is missing (`ConnexPPKVGuard.check`).
* Missing rows still go through the forward (the batch shape is fixed), but they are released and their token ids blanked, so the garbage lands only in the null block or a private block and nothing is marked computed in the content-addressed prefix cache. The ids travel downstream in `cx_missing` (each stage unions its own) and the last stage returns them.
* Stage 0 attaches the ids to its `ModelRunnerOutput` (`cx_reprefill_req_ids`, same process with UniProcExecutor). `Scheduler.update_from_output` skips the token sampled for them in that step and sets `num_computed_tokens = 0`; the request stays RUNNING and keeps its stage-0 blocks. This is the same pattern vLLM uses for KV-load failures (`failed_kv_load_req_ids`), so the next `schedule()` gives the request prompt + generated tokens as a (possibly chunked) prefill on the current chain, the runner drops the discarded token through its stock "num_output_tokens < len(output_token_ids)" alignment, and decoding continues where it stopped. We rewind to 0 rather than resuming from a stage-0 prefix-cache hit because a partial context would again be missing on the new downstream replica. Preemption (`_preempt` / resumed requests) was not usable: a request preempted in `update_from_output` is still in `prev_step_scheduled_req_ids` and in the persistent batch, which trips the resume assertions in both the scheduler and the runner.
* Stage 0 classifies a multi-token step of a request already past its prompt (a later chunk of a re-prefill) as prefill, otherwise its token ids would not go downstream.
* Bound: a request rewound more than `CONNEX_PP_REPREFILL_MAX` times is finished with `finish_reason=abort` (a clean error to the client, never a silent wrong decode).
* Communicator fix found by the stage-1 kill test: after stage 0 confirmed its stage-1 peer dead (suspect + data-path timeout), `_get_peer_endpoint` recomputed the rank-based choice over the router's list, which still contained the dead replica until its lease expired, so it re-selected it and the engine died after 5 attempts (all 16 in-flight requests failed with HTTP 500). Replicas in `_deregistered_replicas` are now skipped unless nothing else is left; registration clears the entry.

Why not mark everything bound to the departed chain at stage 0 proactively: stage 0 only sees its own downstream neighbour's failover; a stage-2 failover happens inside stage 1's communicator. Detection at the stage that lacks the KV covers every hop and also the restart / reclaim / prefix-cache cases, at the cost of one wasted step per affected request.

Cost: `cx_ctx` is one list of ints per step (built from `self.requests`, O(running requests)); the check is a dict lookup per request on stages 1+. Under 900 requests of QPS 4 load there were 0 false positives (`no KV here` never logged).

## Evidence on the cluster (2026-10-17, 4 stages x 2 replicas, connexte, A40)
How to reproduce: `benchmarks/k8s/failover_correctness.py run` sends 16 fixed greedy requests (300 tokens, ignore_eos) to stage 0 of replica 1 (`http://<stage0-replica1>:5101`), with `--kill` running a script that scales the target deployment to 0 and runs `kill -9 -1` inside its container (a SIGTERM via scale alone lets the engine finish the batch during the 15 s grace period, so no failover happens), then `score --url http://<stage0-replica0>:5100` teacher-forces every completion through the other chain (prompt + generated ids, echo, logprobs=1) and counts generated tokens more than 0.5 nats below the argmax. Exact-match comparison against a churn-free run is reported too, but greedy decoding is not batch invariant: two churn-free runs agree on 12-15 of 16 requests, with near-tie divergences as early as token 3. Do a clean restart of all 8 pods before each kill run: re-adding a single killed pod under the same replica identity breaks its Mooncake peers ("Mooncake transfer failed with code -1"), an existing limitation unrelated to this patch.

(*) K=1 needs `CONNEXTE_RECV_RETRIES=15`: the fork's K=1 retry loop gives up after 5 x 3 s, before the router's lease-based failover (~20-30 s for a SIGKILL), and its engine dies (all requests HTTP 500), with or without this patch. The K>1 loop keeps retrying while the downstream is healthy (commit 81ed83c).

Logs show the mechanism: stages 2 and 3 of chain 0 log `External PP stage N: 4/4 request(s) of a decode step have no KV here ...` four times (one per microbatch at K=4, once with 16/16 at K=1), stage 0 logs `Stage 0: 4 request(s) lack downstream KV; re-prefilling them`, and requests finish 10-30 s later than churn-free ones (failover wait plus one recompute).

The engine fixes of cdc955b were validated on the same deployment: greedy outputs of "The capital of France is" / "Write a haiku about the sea:" (24 tokens, temp 0) are byte-identical to edcf1ef (before the fixes) on both chains; under 2 x 450 requests of the QPS 4 trace stages 1-3 log `finished notices=768 released=384 deferred=0 revived=0 live_reqs=2-4` and the allocator logs `reclaimed_reqs=0 exhausted=0 live_reqs=2-7` throughout, with stage 0 running 3-4 requests.

## Limitations
* The recompute costs one prefill of prompt + generated tokens per affected request, on stage 0 too (its own KV was fine, but a partial context would not match the new downstream replica). A smarter version could ask stages for the longest prefix they hold.
* The rewind counter never decays: a request that survives more than `CONNEX_PP_REPREFILL_MAX` separate failovers is aborted.
* `cx_reprefill_req_ids` rides on the in-process `ModelRunnerOutput`; with a multiprocess executor (TP > 1 on stage 0) the attribute would not survive serialization and requests would be decoded as before (still detected and logged downstream).
* Spec decode and structured output are not covered (stage-0 pipelining excludes them anyway).

## Fast handover: from 18-27 s to 2-3 s (2026-10-19, branch fast-handover)
With re-prefill correct, the handover (kill -> first resumed token on the affected chain) was dominated by detection, not recompute. Timeline of a stage-1 SIGKILL at K=1 in the old logs: recv timeout at +3 s (re-send to the same dead peer), UNHEALTHY at +5 s (6 s lease, 1 s heartbeat) which only marked a suspect, more 3 s timeouts, ENDPOINT_DEREGISTERED at +16 s (lease + 10 s grace), then the step still had to wait out its current 3 s recv before re-sending: ~18.5 s. At K=4 a stage-2/3 kill was ~27 s because stage 0 never times out on its direct peer, so it waited for the deregistration, and then each of the 4 in-flight micro-batches waited its own 3 s timeout in turn (+9 s). Re-prefill itself is <1 s.

Why a missed lease was not trusted: a busy engine starves its heartbeat thread (GIL), and fixed short timeouts killed healthy chains under load before. The fix keeps that rule but adds a cheap, reliable confirmation: a TCP connect to the peer's ZMQ port (`_probe_tcp`). The listening socket is served by the kernel, so a live but starved engine still accepts, while a killed process on host networking refuses instantly. What changed (`integrations/vllm/connexte_communicator.py`, `CONNEXTE_FAST_HANDOVER=1` by default):
* UNHEALTHY of our direct downstream peer, or a data-path recv timeout, triggers the probe; refused means fail over now (no grace). A peer that accepts is kept, so a slow step is never treated as a dead peer, and the adaptive timeout max(base, 3x slowest recent step) is unchanged.
* Stage 0 also probes UNHEALTHY replicas of stages >= 2 (their death loses its in-flight steps although its own peer is fine); the stage right upstream of the dead one fails over by itself on the same event.
* A confirmed death bumps a chain epoch (direct peer) or remote epoch (farther down). Every stage-0 send records the epochs; a waiting recv polls in 50 ms slices and returns None as soon as its step was sent on a failed chain (remote: once the step is overdue, so steps of the surviving chain are not re-sent). The K>1 engine loop (`patch_external_pp_stage0_inflight.py`) then re-sends all stale in-flight slots at once, oldest first, instead of one timeout each. Correlation ids, reply caches and the stale filter are unchanged, so re-sends stay idempotent.
* Lease: heartbeat 0.5 s, router lease 2 s (`deploy/k8s/manifests.py`); grace stays 10 s since it is no longer on the critical path. In a steady QPS 8 K=4 run no stage logged a missed lease.

Two K=1 bugs surfaced by the faster path (first matrix run: 5/12 K=1 runs lost every request, 3 had non-argmax tokens). The fork runs stage-0 send and recv on different threads: (1) `_drain_acks` on the send thread could take a message the recv thread had just polled, and the recv reported "timed out after 0 ms", re-sending a step; (2) the recv for step N+1 could start before the send thread set `_pending_corr`, so a late duplicate reply of step N was accepted as N+1 (wrong hidden states, then a crash). Fixed: a polled-then-missing message is not a timeout (it is in the stash), K=1 stage 0 drops any reply with an id <= the last answered one, and K=1 judges staleness by a failover during the wait. Unit tests: `tests/test_fast_handover.py`.

Results (4 stages x 2 replicas on three A40 nodes, kill-after-100-tokens, failover_correctness score, handover median / max s; before: 3 reps; after: K=4 2 reps, K=1 2 reps after the K=1 fix, plus 1 K=4 regression rep):

    K=4 stage 1   15.4-18.4         1.9-2.8

Reproduce: deploy two 4-stage replicas with `deploy/k8s/manifests.py`, clean restart of the 8 pods, warm-up, then `handover.py --kill "kill.sh STAGE 1" --kill-at-tokens 100` and `failover_correctness.py score`; in the stage-0 log look for `is dead (probe refused)` followed within ~0.2 s by `re-sending in-flight step` and `lack downstream KV; re-prefilling`. What remains (~2-3 s) is lease expiry (2 s + up to 0.5 s check interval) or the 3 s data-path timeout plus one re-prefill; going lower needs a shorter lease or a push from the dying pod, both of which trade against false suspicion under load.

## False "no KV here" on same-step shared prefixes (2026-10-19, branch kv-guard-fix)
Symptom: on a cold n=32 batch, before any kill, stages 1+ logged `6/30 request(s) of a prefill step have no KV here` (failover_correctness.py reuses 24 topics, so requests 24-31 share their first block with 0-7). Why: stage-0 vLLM caches full blocks at schedule time (`vllm/v1/core/kv_cache_manager.py` ~327, `cache_blocks(request, num_computed + num_new)`), so the second of two requests sharing a prefix in the same step gets num_computed_tokens=16 and only its suffix is sent with cx_ctx=16. Downstream, `ConnexPPKVGuard.own_prefix` trusted only `alloc.computed`, which `mark_computed` fills after the forward, so a block written earlier in the same step never counted. The row was blanked and re-prefilled for nothing, and since `forget` dropped its kv_len, every in-flight step (K=4) carrying it was flagged again, each one counting toward `CONNEX_PP_REPREFILL_MAX`.

Fix: `check()` now gets `num_scheduled` and, for prefill steps, computes (to a fixpoint) the hashes of full blocks in `toks[:ctx+num_scheduled]` of rows that are themselves valid, and `own_prefix` also accepts those. This is sound because `alloc.prefill` maps equal hashes to the same physical block and the forward writes all rows' KV before attention reads it (stage-0 vLLM relies on the same property). Earlier steps need nothing extra: a stage runs steps in order and marks them computed before checking the next one, so K>1 only cascaded as a consequence of the same-step false positive. A producer that is itself missing, or schedules only part of a block, vouches for nothing, so a genuine miss after failover (fresh replica, empty cache) is still flagged. Verified by unit tests in `tests/test_reprefill.py` (same-step pair either order, producer chain, true miss on fresh replica, K>1 in-flight steps); Verified on GPUs: Two cold n=32 batches without kills gave 0 `no KV here` lines on all 8 pods and 0 re-prefills. In the K=4 and K=1 kill matrix (N=32, stages 1/2/3), each run re-prefilled exactly 32 requests (before: 32-36 per run), with 0 non-argmax tokens and a 2.2-2.9 s handover.
