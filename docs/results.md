# Results

This page collects the measurements behind Connex v0.1.0 on a vLLM pipeline
(sections 1-6), prefill-decode disaggregation on upstream vLLM and SGLang
(section 7), RL weight sync (section 8), agent session migration
(section 9), expert parallelism (section 10), tensor parallelism with
group-level recovery (section 11), PD, TP and EP across hosts and with
mixed GPUs (section 12), and pipeline parallelism on upstream vLLM without
the fork (section 13). Sections 1-6 cover
steady-state latency and throughput with one and four pipeline steps in
flight, correctness and latency of in-flight request handover when a
downstream stage dies, goodput while a replica churns (with and without the
optional resume proxy), and the cold-start cost. Unless a table says
otherwise, every cell comes from repeated runs, each from a clean restart of
the router and all stage pods, and shows the mean with the [min-max] range
across repetitions.

## Setup

* **Model and pipeline.** Llama-3-8B (bf16), 4 external pipeline stages of 8
  decoder layers each, one GPU per stage, tensor parallelism 1. Two pipeline
  replicas for the handover and churn experiments, one for steady state.
* **Hardware.** NVIDIA A40 (48 GB) nodes with 4 GPUs each and ConnectX
  InfiniBand NICs (100 Gb). Eight stage pods are spread over three nodes so
  that the two pods of the same stage never share a node; within a replica
  two stages share a node (on separate ports). Some hops use a GPU that is not
  next to the NIC (slower PCIe path). The GPUs are shared with other tenants,
  and each stage runs at a 0.6 memory fraction.
* **Software.** The external-PP vLLM fork with every Connex engine patch
  (`VLLM_PATCHES=all`, `integrations/vllm/patches/apply_all.py`), the ConnexTE
  communicator (Mooncake Transfer Engine over RDMA with GPUDirect, Connex
  front-router as control plane), deployed with `deploy/k8s/manifests.py` on
  plain Kubernetes with host networking.
* **Connex settings.** `CONNEX_PP_DOWNSTREAM_GRAPHS=1`;
  `CONNEX_PP_INFLIGHT=1` (K=1) or `4` (K=4); re-prefill on
  (`CONNEX_PP_REPREFILL=1`, at most 8 per request); fast handover on
  (`CONNEXTE_FAST_HANDOVER=1`); heartbeat every 0.5 s, router lease 2 s,
  unhealthy grace 10 s; `CONNEXTE_RECV_TIMEOUT_MS=3000`,
  `CONNEXTE_RECV_RETRIES=15`; logprobs warm-up on (`CONNEX_WARMUP_LOGPROBS=1`)
  except where the cold-start section says otherwise.
* **Workload.** Open-loop replay of gamma-arrival traces (CV 1.0, mean QPS 2,
  4 or 8, generated by `benchmarks/k8s/gen_trace.py`), fixed output length
  (`ignore_eos`), streaming, 60 s client timeout. **Goodput** is the share of
  requests that complete within the timeout; latencies cover completed
  requests only. The traces are 1 to 2.5 minutes long: a steady-state run
  replays one once (119, 450 or 1,170 requests at QPS 2, 4 or 8), a churn run
  repeats it to span several down/up cycles (476, 900 or 2,340 requests).
  Request lengths come from a production-like distribution: 12-2,048 context
  tokens (mean 338) and 3-439 generated tokens (mean 44).
* **Sample traces are heavier.** The files in `benchmarks/traces/` (`make
  traces`, `gen_trace.py` defaults) have the same arrival process but
  uniform lengths, 128-1,024 context and 32-256 generated tokens (mean 146,
  about 3x the traces above), and last 240 s. Do not compare them with the
  tables: on the K=4 setup of section 1 they gave 7.05 s mean / 12.6 s P99
  E2E at QPS 2, 7.51 / 15.2 s at QPS 4, and 19.6 / 39.2 s at QPS 8, where the
  pipeline is saturated (100% goodput in all three, one run each).

## 2. In-flight handover: correctness and latency

Two replicas. N=32 greedy requests (temperature 0, `ignore_eos`, 300 tokens,
streamed with token ids) go to stage 0 of replica 1, and 8 more to replica 0
(the "unaffected" requests). When every affected request has at least 100
tokens, one downstream stage of replica 1 is SIGKILLed. Every completion is
then teacher-forced through the healthy replica (prompt plus generated ids,
echo, logprobs); a token is **non-argmax** when it is more than 0.5 nats
below the argmax given its own prefix. A request decoded without its earlier
KV produces such tokens; a correct one does not. **Handover** is the time from
the kill to the end of the largest inter-token gap that ends after it.

One repetition per cell, fresh deployment with warm-up:

| K | killed stage | completed | re-prefilled requests | non-argmax tokens | worst gap (nats) | handover median / max (s) | unaffected: completed, worst stall |
|---|---|---|---|---|---|---|---|
| 4 | 1 | 32/32 | 32 | 0 / 9,600 | 0.125 | 2.21 / 2.27 | 8/8, 0.67 s |
| 4 | 2 | 32/32 | 32 | 0 / 9,600 | 0.125 | 2.57 / 2.66 | 8/8, 1.94 s |
| 4 | 3 | 32/32 | 32 | 0 / 9,600 | 0.125 | 2.24 / 2.34 | 8/8, 0.90 s |
| 1 | 1 | 32/32 | 32 | 0 / 9,600 | 0.125 | 2.80 / 2.90 | 8/8, 0.79 s |
| 1 | 2 | 32/32 | 32 | 0 / 9,600 | 0.125 | 2.89 / 2.98 | 8/8, 0.78 s |
| 1 | 3 | 32/32 | 32 | 0 / 9,600 | 0.125 | 2.89 / 2.96 | 8/8, 0.58 s |

Every affected request is re-prefilled exactly once. In the stage-0 log a
`is dead (probe refused)` line is followed within ~0.2 s by the re-send of
the in-flight steps and the re-prefill. The remaining 2-3 s is failure
detection: router lease expiry (2 s plus up to one 0.5 s check) or a 3 s
data-path timeout, followed by one re-prefill (well under 1 s). The
surviving replica completes all its requests; its worst stall during the
failover (0.6-1.9 s) is in the range of a normal prefill step.

**Larger correctness campaign.** A wider matrix ran before fast handover was
added (6 s lease, failure confirmed only by data-path timeouts), with the
same re-prefill logic: K=4 and K=1, N=16 and 32, stages 1, 2 and 3 killed
separately, 3 repetitions each, 72 kill runs in total. Every affected request
completed (1,728/1,728), and teacher-forced scoring of all 518,400 generated
tokens found **0 non-argmax tokens** (worst gap 0.25 nats). Requests on the
surviving replica were never lost (576/576). Handover then took 15-19 s
(stage 1, or any stage at K=1) and ~27 s (stage 2 or 3 at K=4); fast
handover brings this to the 2-3 s above. For contrast, the same kill with
re-prefill disabled produces 596 non-argmax tokens out of 4,800, with gaps up
to 21.5 nats (`docs/design/reprefill-on-failover.md`).

Exact-match comparison with a churn-free reference is a noisy signal:
greedy decoding is not batch-invariant, so two churn-free runs of 32
concurrent requests agree on only 24-28 of 32 completions. All divergences
after a kill are near-ties (≤ 0.25 nats), which is why the teacher-forced
score is the primary check.

## 3. Churn: goodput with and without the resume proxy

Two replicas, K=4. Every 60 s for 240 s, replica 1 is either scaled to 0 and
back (**hard**: its pods are killed and come back cold) or deregistered and
re-registered at the router (**soft**). QPS 8 has 2 repetitions; QPS 2 and 4
one each. "+ proxy" is the same deployment with the load sent through
`connex.serving.proxy` (`PROXY=local`). Lost requests are split into those
that failed before their first token (0-token) and after (mid-stream).

| churn | proxy | QPS | goodput % | mean E2E (s) | P99 E2E (s) | mean TTFT (ms) | lost 0-token | lost mid-stream | proxy resumes / retries |
|---|---|---|---|---|---|---|---|---|---|
| hard | no | 2 | 99.4 | 1.56 | 5.50 | 100 | 0 | 3 | - |
| hard | no | 4 | 99.6 | 2.00 | 7.17 | 113 | 0 | 4 | - |
| hard | no | 8 | 99.2 [99.0-99.4] | 2.47 [2.46-2.48] | 9.70 [9.68-9.72] | 110 | 2, 5 | 12, 19 | - |
| hard | yes | 2 | **100.0** | 2.03 | 10.67 | 454 | 0 | 0 | 7 / 0 |
| hard | yes | 4 | **100.0** | 2.25 | 10.36 | 343 | 0 | 0 | 3 / 1 |
| hard | yes | 8 | **100.0** [100-100] | 2.60 [2.58-2.63] | 10.51 [10.41-10.62] | 113-122 | 0 | 0 | 12+13 / 1+1 |
| soft | no | 8 | 100.0 [100-100] | 2.80 [2.79-2.82] | 11.22 [11.15-11.30] | 110 | 0 | 0 | - |

* Downstream failures never lose a request: every request lost without the
  proxy was on the killed replica's **own stage 0**, which disappears together
  with its API server under hard churn. The few 0-token losses are
  connection resets at the kill; mid-stream losses end when the pod's
  15 s termination grace period runs out and the kubelet SIGKILLs it.
* The proxy recovers all of them: 0 failed requests in more than 6,000
  proxied churn requests, and 0 failed resumes. Resumes use the token-id path
  (`return_tokens_as_token_ids`), so greedy output is unchanged.
* The QPS 8 proxy row was measured with the logprobs warm-up (section 5). The
  QPS 2 and 4 proxy rows were measured before it, so their mean TTFT and P99
  include one ~8.5 s compile stall per cold engine (at start and after each
  rejoin); with the warm-up the QPS 8 mean E2E dropped from 2.86 to 2.60 s and
  the P99 from 11.51 to 10.51 s.
* The surviving replica's latency under churn is the same as in steady state:
  the cold rejoin of the killed replica does not disturb it.

## 4. Resume proxy: steady-state cost

Churn-free, one replica, K=4, QPS 8, with the logprobs warm-up:

| | reps | goodput % | mean E2E (s) | P99 E2E (s) | mean TTFT (ms) |
|---|---|---|---|---|---|
| no proxy | 1 | 100 | 2.64 | 10.03 | 120 |
| proxy (token ids, default) | 3 | 100 / 100 / 98.7 | 2.67-2.70 | 10.10-10.21 | 116-127 |

The proxy adds ~0.03-0.05 s mean and ~0.1-0.2 s P99 E2E. It made 0 resumes
and 0 retries in churn-free runs, so its 2.5 s idle timeout never fired on a
live replica. One of the three proxy repetitions lost 15 requests with HTTP
502: within one second the single stage-0 API server reset connections
(`Connection reset by peer`), and with only one endpoint the proxy used up
its 4 attempts in under 0.5 s. The engine logs of that run were not
captured, so the cause is open; a rerun with logs was clean. The retry
budget does not span a ~1 s blip of a single replica (see Limitations in
the README). With `--no-token-ids` (no logprobs requested) the proxy was
indistinguishable from no proxy before the warm-up existed (2.60 vs 2.59 s
mean, 9.98 vs 9.97 s P99).

Per-chunk overhead on one host with a fake backend (`benchmarks/proxy_overhead.py`,
64 tokens per request, TPOT 10 ms; the backend, proxy and client are
separate processes):

| concurrency | added p50 / chunk | added p99 / chunk | added p99, past the first 4 chunks | added TTFT p50 |
|---|---|---|---|---|
| 1  | 0.25 ms | 0.52 ms | 0.40 ms | 2.1 ms |
| 16 | 0.18 ms | 1.9 ms | 0.54 ms | 5.9 ms |
| 64 | 0.13 ms | 2.6 ms | 1.2 ms | 13.9 ms |

## 5. Cold start

The vLLM fork compiles the logprobs rank op (`batched_count_greater_than`,
`@torch.compile(dynamic=True)`) lazily, so on a fresh engine the first request
that asks for logprobs stalled 8.6-9.1 s. The resume proxy (which requests
`logprobs=0` to get token ids) and the correctness harness hit it on every
fresh deploy and after every hard-churn rejoin. Engine patch 15
(`patch_external_pp_warmup_logprobs.py`, `CONNEX_WARMUP_LOGPROBS=1` by
default) runs the op for batch sizes 1, 2 and `max_num_seqs` during engine
warm-up, before the API server reports ready.

Fresh 1-replica deploy, 8 concurrent 16-token requests per batch:

| measurement | warm-up off | warm-up on |
|---|---|---|
| first batch plain, second batch logprobs (TTFT) | 0.51 s, **8.57 s** | 0.50 s, **0.078 s** |
| first batch logprobs (TTFT) | **9.08 s** | **0.52 s** |
| logprobs batches of 1, 3, 8, 1 requests in a row | - | 0.46, 0.081, 0.082, 0.052 s |
| added startup (5 cold starts) | 0 | 8.5-8.9 s |

The stall is paid once at startup (about 8.7 s of a ~135 s cold deploy)
instead of by a request. The first request on a cold engine still takes
~0.5 s for other first-request work. No later batch size recompiled.

## 6. connex-rs data plane vs Mooncake

[connex-rs](https://github.com/HeterInfra/connex-rs) is Connex's data plane
in Rust over UCX (its own repository; `pip install "connex-ai[rs]"`).

Same setup as above (4 stages, Llama-3-8B, A40 + 100 Gb InfiniBand,
GPUDirect), with the data plane switched between connex-rs and Mooncake
Transfer Engine (`CONNEX_PP_BACKEND`). Steady state is from one replica,
everything else from two. Mooncake's handover figures come from section 2.

| | connex-rs | Mooncake |
|---|---|---|
| one-sided GPU->GPU read, cross-host, 16 KB / 1 MB / 16 MB | 8-10 us / 98-106 us / 1.69 ms | 9 us / 116 us / 2.0 ms |
| K=4 steady state, QPS 2 / 4 / 8, mean (P99) s | 1.61 (5.63) / 2.01 (7.17) / 2.61 (10.01) | 1.60 (5.61) / 2.04 (7.13) / 2.59 (10.03) |
| closed loop, 128 clients, tok/s | 2530 | 2608 |
| kill -> first resumed token (median per run), K=4, stage 1 / 2 / 3 | 0.01-0.02 / 0.03-0.04 / 0.03-0.83 s | 2-3 s |
| same, K=1 | 0.02-0.03 s for every stage | 2-3 s |
| slowest single request across those runs, K=1 / K=4 | 1.03 s / 0.92 s | |
| failover correctness, N=32, stages 1-3, K=1 and K=4 (18 runs) | all complete, 0 non-argmax tokens | all complete, 0 non-argmax tokens |
| false failovers, 10 min at QPS 8 | 0 | |
| single stage killed and restarted under the same identity | both replicas serve, rejoined stage carries traffic | restart the whole chain |
| hard churn at QPS 8, goodput with / without resume proxy | 100 % / 99.2 % | 100 % / 99.2 % |
| 100 kill/rejoin cycles of a peer against a live stage | fds, RSS, endpoints and registered memory flat | |

The handover gets faster because connex-rs reports the death itself. The
killed process's kernel tears down its UCX connections, and every linked
stage sees an endpoint error within milliseconds. `connex.pp` treats that
as a confirmed death and re-sends the affected in-flight steps at once, with
no lease expiry, data-path timeout or probe in between. The router lease and
the probe remain for hung or partitioned peers. Greedy outputs of the two
data planes agree on 31 of 32 prompts, and two fresh deployments of the same
data plane also differ on one prompt in 16 (batch and cache effects in the
engine). All outputs pass teacher-forced scoring with 0 non-argmax tokens.

Without RDMA, connex-rs works but UCX emulates one-sided reads over TCP,
and that path was several times slower than Mooncake's TCP path. A 1-replica
pipeline forced onto TCP ran QPS 2 at 100 % goodput, with a 2.42 s mean
instead of 1.61 s. That is why `CONNEX_PP_BACKEND=auto` uses connex-rs only
when an RDMA device is usable.

Not covered: node loss or a network partition (no RST), where detection
falls back to the transport heartbeat (1 s / 3 s) or the router lease plus
probe.

## 8. RL weight sync

`connex.rl` ([`rl.md`](rl.md)). Hardware as above: A40 GPUs, 100 Gb
InfiniBand, GPUs shared with other tenants. One run per configuration;
"warm" is the mean over the rounds after the first (the first round also
opens the connections and registers memory), with [min-max].

**Transfer only, across nodes** (`benchmarks/rl/weight_sync_bench.py dist`,
pods from `benchmarks/rl/k8s_weight_sync.py`). Synthetic bf16 weights sized
like the named model, already on the trainer GPU; the time runs until every
receiver holds the whole model on its GPU. Connex: all receivers start at
once, so all of them read from the trainer (the tree only forms when
receivers start at different times, see below). NCCL: one process group,
the trainer broadcasts the packed buffer in 64 MB chunks. **The NCCL column
is NCCL over IPoIB sockets** (`NCCL_IB_DISABLE=1`): NCCL over IB verbs failed
at the first collective between the pods of this image (see the insights in
[`design/rl-and-agent-migration.md`](design/rl-and-agent-migration.md)), so
this is not a comparison with NCCL over IB verbs.

## 10. Expert parallelism (MoE)

`connex.ep` ([`ep.md`](ep.md)), `benchmarks/ep/`. SGLang: see the end of
this section. vLLM 0.32.0, OLMoE-1B-7B
(64 experts, top-8, 16 MoE layers, bf16), one EP group = tensor and expert
parallel over two A40s of one host (PCIe, no NVLink), 0.6 memory fraction,
CUDA graphs on. Connex runs vLLM with `--enable-eplb`, 64 redundant experts
(every expert on both ranks: either rank can carry all of them) and EPLB's
own rebalancing off; its placement table drives vLLM's expert maps through
the worker extension. Load: 128 or 256 text prompts, 128 greedy tokens each
(`ignore_eos`), 32 concurrent, streaming. **Correctness** is the
teacher-forced check of `pd_bench.py score` on a freshly started default-EP
server: every generated token must be the argmax given its own prefix
(0.5 nat tolerance for near-ties). One run per row unless stated.

**Steady state.** Throughput of the whole load (two runs where given):

| configuration | tokens/s | TPOT p50 | non-argmax tokens |
|---|---|---|---|
| vLLM default EP (no EPLB) | 2,317 / 2,338 | 13.1 ms | 0 |
| EPLB, 0 redundant, Connex extension | 2,314 | 13.2 ms | |
| EPLB, 32 redundant, every replica routed | 1,889 | 16.3 ms | |
| EPLB, 64 redundant, every replica routed (first version) | 1,590 / 1,572 | 19.6 ms | 0 |
| EPLB, 64 redundant, Connex `active_replicas=1` (standby) | 2,299 / 2,307 | 13.3 ms | 0 |

The control path costs nothing measurable (row 2). Routing tokens to every
replica does (rows 3-4): vLLM hashes tokens over all copies, so each decode
step reads both copies of a hot expert. With one routed replica per expert
and the second copy as warm standby the redundant deployment runs within
1 % of the default, and the standby copies take over in the next epoch when
a rank drains or fails, with no weight movement.

**Drain a rank under load, then rejoin it.** At t = 4 s rank 1 is drained;
then all 64 of its expert slots are overwritten with NaN, so any token still
routed there would wreck its output; 6 s later rank 1 rejoins: its slots are
refilled from rank 0 (1,024 expert-layer copies, 12.9 GB) and routed to
again. 256 requests, all completed in every run.

|---|---|---|

| non-argmax tokens | 0 | 0 |

**Migrate experts under load.** Eight experts (all 16 layers each, 192 MB
per expert) are copied from rank 0 into rank-1 slots one after the other;
then every other replica of them is staged out, so all tokens for these
experts run on the moved weights. 256 requests, all completed, 0 non-argmax
tokens in every run. Per expert:

| | first version | after |
|---|---|---|
| copy, worker side | 17-20 ms (connex-rs, one batch per tensor) | 12.6-13.4 ms (connex-rs, all reads in one wave, or CUDA IPC; bounded by the decode step that runs concurrently) |

controller now adopts the engine's epoch when it attaches, and an engine

**Failover** (rows above the line: RDMA between stages, before the same-host
path; below: with it). 32 closed-loop streaming clients (128 tokens each),
SIGKILL of the active replica 15 s in, the killed replica restarted with
the same command before the next kill (it rejoins as a spare):

| setup | kills | requests completed | errors | largest gap between two tokens, per run |
|---|---|---|---|---|
| PP=2, one host | 10 | 3,168 / 3,168 | 0 | 0.39-0.71 s |
| PP=3, last stage, one host | 2 | 640 / 640 | 0 | 0.46-0.58 s |
| PP=2, three hosts | 2 | 640 / 640 | 0 | 0.43-0.49 s |
| PP=2, one host, CUDA IPC | 5 | 3,968 / 3,968 | 0 | 0.34-0.60 s |
| PP=3, middle stage, one host, CUDA IPC | 2 | 576 / 576 | 0 | 0.69 s and 2.61 s |

All 32 requests in flight at every kill completed. A kill is detected by
connex-rs within milliseconds (the dead process's connections reset); stage
0 completes the steps in flight as lost, reports the replaced stage's KV as
lost, and vLLM's scheduler recomputes every running request on the new
route. Correctness runs with a kill 3 s into 16 greedy requests: 17 of 18
completed with 0 tokens off the argmax (one hung, see below).

The middle-stage kill is the case CUDA IPC makes delicate: the next stage
has the dead replica's ring mapped, and an open mapping keeps that GPU
memory allocated. The receiver releases the flags at once (streams waiting
for the dead peer go on with garbage that the recompute discards) and
unmaps only after every stream that used the channel has passed that point;
unmapping or unregistering earlier crashed the stage (CUDA error in a later
stream operation). The killed replica then restarted on the same GPU each
time.

**Kill under load, NCCL vs Connex** (one host, same 32 clients, 150 s, kill
15 s in; 3 kills per row). Stock vLLM runs under a restart loop (a
supervisor that relaunches `vllm serve` when it exits); "down" is the time
from the kill until a 1-token request succeeds again, "tokens lost" the
tokens already streamed to requests that did not complete, "completed" the
requests that finished all 128 tokens in the 120 s after the kill.

| setup, what is killed | in flight completed | tokens lost | down | completed in 120 s | tokens/s in 120 s |
|---|---|---|---|---|---|
| PP=2 NCCL, stage-1 worker | 0 / 32 (x3) | 1,794 / 2,206 / 2,473 | 57.5 / 63.3 / 62.0 s | 448 / 411 / 416 | 478 / 438 / 444 |
| PP=2 Connex, active stage-1 replica (spare) | 32 / 32 (x3) | 0 | 0 s (largest gap 0.34 / 0.42 / 0.46 s) | 864 / 871 / 876 | 922 / 929 / 934 |
| PP=2 x TP=2 NCCL, one TP rank of stage 1 | 0 / 32 (x3) | 547 / 1,481 / 1,170 | 60.7 / 60.1 / 60.6 s | 768 / 777 / 773 | 819 / 829 / 825 |
| PP=2 x TP=2 Connex, one TP rank of stage 1, no spare | **0 / 32 (x3), failed** | 3,189 / 0 / 0 | not recovered | 0 | 0 |

Stock vLLM reloads the model in 49-50 s after the supervisor relaunches it
(start to ready); the rest of the outage is detecting the dead engine and
the exit. Every request in flight is lost and the clients see errors.

**The PP=2 x TP=2 Connex rows failed.** With no spare replica on this host
the killed stage was restarted by a restart loop (ready again after 26 s),
and stage 0 should have resumed on it. Instead stage 0's two TP ranks hung
in the in-group broadcast of the sampled tokens (NCCL timeout after
10 min); the first run's 32 requests timed out, and in the next two the API
was already down. A failure-event bug made it worse and is fixed (a late
"failed" event about the killed incarnation marked the restarted replica
dead again and again, each time recomputing every request; events are now
confirmed with a ping), but the hang remains: failover with TP > 1 on stage
0 is not working. TP > 1 on a downstream stage, and stage 0 at TP=1, are
unaffected.

Earlier findings: in one of 28 kills of the first series (RDMA, one host)
all 16 requests of a correctness run hung; the cause found since (the same
late failure event repeatedly marking a live replica dead) fits, but was not
confirmed for that run. An earlier version that only preempted the
requests, without evicting their blocks from the prefix cache, completed
every request but left 59 tokens off the argmax in 14 of 16 requests.

**Not covered.** A replica shared by several pipelines (the fork path
supports it; here a replica serves one stage 0 at a time), failover with
TP > 1 on stage 0 (fails, above), more than one failure at a time, stage 0
failures (the API instance; use the resume proxy of section 4), PP across
hosts with more than two stages.

## How to reproduce

Deploy (see `deploy/k8s/README.md`):

```bash
G() { python deploy/k8s/manifests.py --namespace connex --image REG/connex-vllm:TAG \
   --model-host-path /models/Llama-3-8B --num-stages 4 \
   --host-network --ib --protocol rdma --gpu-select nic-local \
   --set CONNEX_PP_INFLIGHT=4 --set CONNEX_PP_DOWNSTREAM_GRAPHS=1 "$@"; }
G router --router-node NODE_A | kubectl apply -f -
G pipeline --prefix cte --nodes NODE_A,NODE_B,NODE_C,NODE_A | kubectl apply -f -
# replica 1 of each stage, on a different node than replica 0 of that stage
G stage --prefix cte --stage 0 --replica 1 --node NODE_B | kubectl apply -f -   # ... stages 1-3
benchmarks/k8s/wait_ready.sh cte
```

Steady state and closed loop:


## Not covered

* Single repetitions at churn QPS 2 and 4 and in the N=32 handover matrix.
* Soft churn only at QPS 8 and without the proxy.
* The proxy was run on the client host (`PROXY=local`), not as an in-cluster
  pod (`deploy/k8s/manifests.py proxy`).
* Tensor parallelism > 1 in the multi-host k8s setup of sections 1-6 (TP is
  covered on one host in section 11), speculative decoding, structured
  output, and more than 8 failovers of a single request (it is aborted with
  an error).
* The KV handover covers decoding; a request still in its first prefill step
  is simply prefilled on the new replica.
* SGLang: only the communication side exists (see
  `docs/design/sglang-adapter.md`); no end-to-end numbers.
